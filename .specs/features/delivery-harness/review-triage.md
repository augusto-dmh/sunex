## Changes made alongside the triage (not review findings)

- **One commit-message checker.** The quality-tooling PR adds `scripts/check-commit-msg.sh`, which CI runs on every commit of a pull request. `validate_metadata.py` duplicated its header, scope and attribution rules with different details: a free-form scope list, and a different reading of "generated with". The repository script is now the source of truth for those rules. When it exists, `validate_metadata.py` hands every commit message and PR title to it and keeps only what that script does not check: the required body, the single `Assisted-by: Claude Code` trailer, internal references and branch names. Without the script (on `main` before that PR merges), the built-in rules apply. Rejected option: making the shell script call the Python validator. Human contributors and CI would then depend on an agent skill's internals, and the shell script is the one CI already runs.
- **Pull request updates use REST.** `gh pr edit` currently fails on a GitHub GraphQL deprecation, so `sunex-finalize` updates titles and bodies with `gh api -X PATCH repos/{repo}/pulls/{N} -F body=@<file>`.
- **Scopes.** The quality-tooling checker's scope list has no `skills` or `specs`. The skills now say "a scope the repository checker accepts", and the headers they prescribe (triage and landing commits) carry no scope, so they pass under any list. This PR's own commits use `skills`; aligning the checker's list is left to the coordinator (see the ship report).
